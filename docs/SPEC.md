# Relay — requirements and design decisions

Build a small multi-app mail relay ("Relay"), Node.js 20 + MySQL, with a minimal admin interface. It will run on Namecheap shared hosting (cPanel "Setup Node.js App" / Passenger) at https://relay.companysite.site. Its job: many websites and apps on GoDaddy cannot send email because GoDaddy blocks outbound SMTP ports (25/465/587); they can make HTTPS requests, so they POST each message to this relay, and the relay sends it through that site's own SMTP mailbox. Each site/app gets its own settings and its own API key.

## CORE CONCEPTS
- App = one website or piece of software. Fields: name, notes, enabled on/off, SMTP host/port/encryption (SSL 465, STARTTLS 587, none)/username/password, From address and From name (the relay always sends as this; the caller cannot spoof another sender; optionally a short list of allowed From addresses), optional Reply-To default, limits (messages per minute and per day, max message size with attachments, e.g. 10 MB), optional IP allowlist, created/updated times.
- API keys: one active key per app, generated by the relay (at least 32 random bytes, shown ONCE on creation, stored only as a hash). "Regenerate key" makes a new key and, optionally, keeps the old one working for a short grace period (choose: none, 1 hour, 24 hours) so a site can be updated without downtime; "Revoke" stops a key immediately. Show the key's prefix and last-used time, never the full key again.
- SMTP passwords are encrypted at rest (AES-256-GCM) with a master key from an environment variable; never shown again after saving (only "change password").

## API
1. POST /v1/send, header "Authorization: Bearer <api key>", JSON body: to (string or array), cc, bcc, reply_to, subject, html, text (optional; generate from html if missing), attachments [{filename, content_type, content_base64}], message_id (optional idempotency key: a repeated id within 7 days returns the first result and never sends twice). Response 200 {"ok": true, "id": "<relay message id>"} or 4xx/5xx {"ok": false, "error": "<short reason>"}.
2. LEGACY ENDPOINT for an existing PHP app, which must keep working unchanged by only changing its relay URL and key: POST /send.php with headers "X-Relay-Timestamp: <unix seconds>" and "X-Relay-Signature: sha256=<hex HMAC-SHA256(api_key, timestamp + '.' + raw request body)>", JSON body {message_id, to, to_name, subject, html, attachments?: [{filename, content_type, content_base64}]}, exactly one recipient per request. Verify the signature with a constant-time compare over the RAW body, reject timestamps more than 5 minutes off, de-duplicate on message_id. Success must be HTTP 200 with JSON {"ok": true}; failure JSON {"error": "<reason>"} with a 4xx/5xx status. Because the signature needs the plain key, apps using this endpoint need their key kept recoverable: store it encrypted (AES-256-GCM, master key) instead of hashed, and mark such apps "legacy signing" in the admin.
3. GET /v1/health (no auth) returns {"ok": true}.

## SENDING
- Nodemailer, a fresh SMTP connection per message (or a small per-app pool), 30 s timeout, TLS verification on.
- Attachments limited by type (pdf, images, csv, docx/xlsx, txt) and total size.
- Strip CR/LF from every header value; validate addresses.

## ADMIN INTERFACE (minimal, clean, mobile friendly, server-rendered or a tiny SPA)
- Login: one or more admin users, bcrypt/argon2 passwords, optional TOTP 2FA, rate-limited login, secure session cookies, CSRF protection.
- Apps list: name, enabled, today's sent/failed counts, last used.
- App page: edit settings, "Send test email", generate/regenerate/revoke key, copy-paste snippets (curl, PHP, Node) showing how to call the API.
- Log: per message time, app, recipient (masked if you like), subject, size, status, SMTP response or error. Never store bodies or attachments. Keep 90 days, with a cleanup job.
- A simple stats view: sent and failed per app per day.

## SECURITY AND OPERATIONS
- HTTPS only, helmet-style headers, request size limit, per-app and per-IP rate limits.
- Every configuration change goes in an audit log (who, what, when).
- Config via .env: DB credentials, master encryption key, session secret, admin bootstrap user.
- A database migration script, and a README for cPanel deployment: Node app setup, environment variables, MySQL, restarting Passenger.
- Tests for: signature verification (good, bad, old timestamp, tampered body), idempotency, key regenerate with grace period, the From address cannot be overridden, attachment limits.

## Design decisions
1. Idempotency: a failed attempt may be retried with the same message_id; only a sent (or in-flight) message locks the id.
2. Caller `from`: accepted only if it is the app's From or in its allowed list; otherwise 400.
3. /send.php identifies the app by trying every legacy-signing app's valid keys.
4. Extra safeguard: per-app recipient cap (default 50). No log masking. Legacy-signing apps cannot use /v1/send.
5. A message whose outcome is unknown (the process stopped mid-send, or the connection failed after the message data was sent) keeps its message_id locked for the 7-day window (409 "message_id outcome unknown").
6. Attachments: type from the file extension, verified by content sniffing; the caller's content_type is advisory only. Images: jpg, png, gif, webp, heic, bmp, tiff (no svg).
7. Changing an app's SMTP host/port/encryption/username clears the stored SMTP password unless a new one is entered in the same save.
8. /send.php message_id stays optional; requests without one get signature-replay protection.
9. Deliberately not included: blocking auth over encryption "none" (warn only), attachment-count cap, concurrent-send cap, recipients-per-day limit.
